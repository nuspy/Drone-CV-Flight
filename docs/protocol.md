# dronecv wire protocol v1.0

Transport: TCP. Every message is one frame:

```
uint32 big-endian header_length | JSON header (utf-8) | blob payloads (concatenated, in header order)
```

The JSON header always contains `type`, `version`, `msg_id`, `sim_time` and
`blobs` — a list of `{name, dtype, shape, encoding, byte_len}` describing the
binary payloads that follow. Images travel as `jpeg` (or lossless `png`
during capture); depth as raw `float32` row-major arrays. Limits: header ≤ 1
MiB, blob ≤ 256 MiB.

Authoritative schemas: `src/dronecv/protocol/messages.py` (pydantic) and the
mirror `unity/com.dronecv.flight/Runtime/Protocol/Messages.cs`. Golden byte
fixtures generated by `scripts/gen_protocol_fixtures.py` pin the encoding on
both sides; regenerate + commit after any change, and bump `PROTOCOL_VERSION`
(major mismatch = connection refused at handshake).

## Roles and channels

A client declares a `role` in its `hello`:

| role | purpose | truth channel |
|---|---|---|
| `localizer` | consumes sensor frames, estimates pose | **refused** |
| `harness` | test orchestration | granted |
| `capture` | dataset collection | refused |
| `verify` | protocol acceptance checks | refused |

Channels (`subscribe {channels}`): `sensors` (server pushes `sensor_frame`),
`truth` (server pushes `truth_state`, harness only), `control`, `capture`.
The truth restriction is the mechanism that keeps the localizer blind.

## Messages

| type | dir | content |
|---|---|---|
| `hello` | c→s | `role`, protocol version |
| `hello_ack` | s→c | `sim_kind` (unity/headless), `env_id`, `capabilities`, **`geo_meta`** (embedded anchor or null), `camera` {width,height,fov_deg,tilt_deg} |
| `env_info_request` / `env_info` | c→s / s→c | flyable volume bounds (sim frame), ground elevation range |
| `capture_request` | c→s | `pos_sim`, `yaw_deg`, `pitch_deg`, `want:[rgb,depth,sun]` — teleport-capture, does not disturb the drone |
| `capture_result` | s→c | ground-truth pose rendered, UTC, sun/moon az-el; blobs `rgb`, `depth` |
| `subscribe` / `subscribe_ack` | c→s / s→c | requested vs granted channels |
| `sensor_frame` | s→c | `frame_id`, `utc`, `lidar_range_m` (null = dropout); blob `rgb`. **No pose fields.** |
| `command` | c→s | `vel_sim` (m/s, sim world frame), `yaw_rate_dps` |
| `truth_state` | s→c | `frame_id`, pose/velocity/quaternion, `collided` (harness only) |
| `reset` / `reset_done` | c→s / s→c | seed, optional start pose, optional UTC override → deterministic episode |
| `teleport` | c→s | harness only — kidnap test |
| `ping`/`pong`, `error` | both | health, failures |

## Conventions

- Sim frame = Unity local: left-handed, X right, Y up, Z forward. `yaw_deg`
  rotates about +Y, 0 = +Z, positive toward +X.
- `sensor_frame`/`truth_state` pairs share `frame_id` (same tick).
- Determinism: after `reset {seed}`, identical requests produce identical
  results (the acceptance test checks capture determinism explicitly).

## Validating an implementation

`dronecv protocol verify --host H --port P` exercises every behavior above
against a live bridge and prints a pass/fail table — this is the acceptance
test for the Unity side (or any future simulator).
